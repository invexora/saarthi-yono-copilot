# Saarthi API

The FastAPI service exposes its generated OpenAPI document at `/openapi.json` and interactive documentation at `/docs`.

## Identity modes

`SAARTHI_AUTH_MODE=oidc` is required in production. Requests to customer or operations endpoints require:

```http
Authorization: Bearer <signed JWT>
```

The token must contain `sub`, `customer_id`, `iss`, `aud`, `iat`, and `exp`. Optional `roles` control operations access. The verifier resolves rotating asymmetric keys from `SAARTHI_OIDC_JWKS_URL`, accepts only explicitly configured non-HMAC algorithms, and validates issuer and audience. `SAARTHI_AUTH_MODE=jwt` retains HS256 solely for local integration tests and non-production compatibility.

`SAARTHI_AUTH_MODE=development` is explicitly for local synthetic personas. It accepts:

```http
X-Saarthi-Demo-Customer: SBI-772910
X-Saarthi-Demo-Role: customer
```

Customer IDs are always taken from the verified identity context. Customer-scoped request bodies do not accept a `customerId` field.

## Customer lifecycle

1. `POST /api/v1/consent/grant` with `{"purpose":"personalization"}`.
2. `POST /api/v1/orchestrate` with a signal and sanitized details. `segment` is only a local-development hint; eligibility always uses the server-sourced customer segment.
3. Low-risk or review-disabled recommendations are returned in the `presented` state.
4. If `delivery_mode` is `human_review_required`, product and rate fields are withheld. An authenticated `reviewer` or `admin` must decide the item through `/api/v1/reviews/{review_id}/decision`.
5. After approval, the customer calls `GET /api/v1/recommendations/{recommendation_id}`. This atomically reserves the nudge budget and returns the governed offer. Repeated retrieval does not consume budget again.
6. Send the `recommendationId` to `POST /api/v1/decisions/authorize` only after the offer was presented and the customer explicitly confirms it.
7. Send the recommendation ID and returned token to `POST /api/v1/actions/execute`. Success means the configured fulfilment provider returned a downstream completion reference; token issuance alone is never reported as execution.
8. Retry a transient `503` with the same recommendation and token. The execution claim and downstream `Idempotency-Key` prevent duplicate fulfilment. Completed replays return the original provider result.

Decision tokens are returned once and stored only as SHA-256 digests. They expire for execution after five minutes and remain bound to the authenticated customer, recommendation, and explicit action-consent record.

Every orchestration request requires an `Idempotency-Key` header of 8–128 characters. A completed retry returns the original status/body and `Idempotency-Replayed: true`. Transient dependency failures release the claim so the same key can be retried safely; Redis event publication remains deduplicated.

Each orchestration response includes a deterministic `decision_outcome`, machine-readable `reason_codes`, and individual `policy_checks`. These cover trusted-context freshness, server-side segment binding, product-rule matching, affordability, approved policy provenance, safety-rate caps, vulnerability routing, and mandatory human oversight independently of generated text. The public `decision_context` contains provenance and calculated ratios; raw income and obligation values never cross the API response boundary.

Actionable responses also carry a `customer_presentation` generated by the decision service. The same `customer-presentation-v1` object is persisted in recommendation evidence and contains the product-bound title, body, action label, action-consent text, and neutral success wording. The connected browser retrieves this persisted recommendation before displaying an action and rejects missing, expired, support-only, or product-mismatched presentation evidence. Authorization and fulfilment responses must preserve the displayed recommendation and product identities or the browser fails closed.

Synthetic catalogue rates remain internal decision/reviewer evidence. Customer orchestration, product-catalogue and recommendation-presentation responses return no rate until an approved, live and versioned SBI pricing/KFS feed is connected.

`support_mode` returns a non-actionable support presentation with `support_only=true`; public product, rate, policy, and recommendation identifiers are withheld. Human-review responses withhold presentation content until an independent approval allows `GET /api/v1/recommendations/{recommendation_id}` to return the persisted evidence.

`signal_evidence` identifies the detector model/version, confidence, feature schema, evaluation, reason codes, and masked-input digest used for the decision. `SIGNAL_PROVENANCE` is a mandatory policy check; missing or mismatched evidence rejects the recommendation. The raw unmasked signal is never sent to the detector.

Revoking personalization consent blocks subsequent offer presentation and authorization. Cross-customer recommendation retrieval returns `404`, preventing recommendation-ID enumeration from revealing another customer's offer.

The web client never turns an API outage into a simulated completion. Local scripted copy and simulated actions are available only when the operator explicitly opens the UI with `?mode=offline-demo`; the status bar then identifies the session as simulation-only.

Consent status, export, revocation, and erasure are available under `/api/v1/consent`. `POST /api/v1/consent/erase` reports `processed` for the explicitly bounded `eligible_saarthi_derived_data` scope. It removes eligible local profiling records while retaining a revoked-consent tombstone and pseudonymous integrity-ledger evidence. It does not claim deletion of regulated SBI banking records, backups, legal holds, or systems outside this prototype.

## Operational access

`/api/v1/metrics` requires `ops` or `admin` and includes Redis consumer lag, pending delivery, dead-letter, active-worker, and durable processed-event metrics. `/api/v1/events/status` exposes the consumer-group SLO state to the same roles. Its SLO is unhealthy when there is no current worker heartbeat, even if lag is temporarily zero. `/api/v1/events/dead-letters` returns failure metadata without customer identifiers, event payloads, or exception messages.

Dead-letter replay is restricted to `admin` through `POST /api/v1/events/dead-letters/{dead_letter_id}/replay` and requires an `Idempotency-Key`. A retry with the same key returns the same replayed event ID and does not publish twice. Replay is recorded in the pseudonymous integrity ledger.

`/api/v1/audit/logs` requires `auditor`, `ops`, or `admin`. These roles are claims from the authenticated identity, not request-body values.

`/api/v1/ready` includes the consumer worker as a required dependency whenever Redis mode is configured. Memory-mode local development reports that dependency as development-ready without requiring a separate process.

## Governed artifacts

Signed product-catalog and policy-registry operations are available under `/api/v1/governance/artifacts`:

- `GET /api/v1/governance/artifacts` requires `auditor`, `reviewer`, `ops`, or `admin` and supports `artifact_status`, `artifact_type`, and `limit` filters.
- `POST /api/v1/governance/artifacts` requires `ops` or `admin`. It accepts `artifact_type`, `version`, `payload`, `signature`, and `signing_key_id`; the signature covers the canonical `artifactType`/`version`/`payload` envelope.
- `POST /api/v1/governance/artifacts/{artifact_id}/decision` requires `admin`; the authenticated principal must differ from the requester.

Artifacts move through `pending`, `materializing`, `active`, `rejected`, and `superseded`. Only one pending or materializing artifact is allowed per artifact type, and only one active artifact exists per type. Approval verifies the stored digest and Ed25519 signature again before applying the feed. Materialization errors return HTTP 503 and leave the artifact pending; a concurrent approval attempt returns HTTP 409. Responses omit envelopes, signatures, requester references, and approver references.

`/api/v1/ready` includes artifact health. In `SAARTHI_ARTIFACT_FEED_MODE=signed`, readiness requires a configured public key and active, materializable product and policy artifacts. `/api/v1/metrics` exposes `saarthi_governed_artifacts_pending` and `saarthi_governed_artifacts_active`.

## Rollout controls

Governed rollout operations are available under `/api/v1/governance/rollout-controls`:

- `GET /api/v1/governance/rollout-controls` requires `auditor`, `reviewer`, `ops`, or `admin` and supports a `control_status` filter.
- `POST /api/v1/governance/rollout-controls` requires `ops` or `admin`. It creates a pending `active`, `shadow`, or `disabled` control for a global, channel, segment, signal, product, or exact model-version scope. Model values use `model_id:model_version` from `signal_evidence`.
- `POST /api/v1/governance/rollout-controls/{control_id}/decision` requires `admin`; the authenticated principal must differ from the requester.
- `POST /api/v1/governance/rollout-controls/emergency-disable` requires `admin` and immediately supersedes pending or active controls for the exact scope.

Control responses omit requester and approver references and PII-mask the reason. `disabled` always implies a zero-percent cohort, while explicit `shadow` always applies to the full matching scope. Partial `active` cohorts are deterministic per customer; excluded customers are evaluated internally as shadow traffic.

New orchestration returns `delivery_mode=rollout_blocked` for a matching kill switch or `shadow_mode` for shadow traffic. These are governed, non-retry outcomes and return HTTP 200. Existing recommendation presentation, authorization, or execution returns HTTP 423 with `rollout_blocked` or `rollout_shadow`. No suppressed request reaches downstream fulfilment. Rollout gauges on `/api/v1/metrics` expose pending approvals, active disables, and shadow/partial-cohort controls.

## Outcome monitoring

`POST /api/v1/monitoring/outcomes` requires `ops` or `admin` and accepts a recommendation ID, source event ID, outcome type, allowlisted source system, evidence digest, occurrence time, and optional bounded impact score. The source event ID is HMAC-referenced for idempotency and is never returned or stored raw. An exact retry returns HTTP 200 and the original observation; conflicting reuse returns HTTP 409. Unknown recommendations return HTTP 404, and occurrence times before recommendation creation or materially in the future are rejected.

`GET /api/v1/monitoring/report` requires `auditor`, `reviewer`, `ops`, or `admin`. It supports 1–365 day windows and `segment`, `signal`, or `product` dimensions. Results contain aggregate counts, rates, net-benefit rate, threshold alerts, the monitoring policy ID/status, and explicit analytical limitations. No endpoint accepts a protected attribute, and no customer-level outcome listing is exposed to operators.

Metrics include total observations, complaints, harms, and current 30-day segment alerts. Customer portability export includes the customer's safe observation fields; erasure removes the observations with their linked recommendations.

## Signal-model governance

`GET /api/v1/governance/signal-model` requires `auditor`, `reviewer`, `ops`, or `admin`. It returns the active model and feature-schema versions, evaluation identity/status, dataset version, sample count, aggregate accuracy and macro metrics, per-category results, and limitations. It never returns evaluation rows or customer inputs.

Production accepts classifications only from the configured SBI adapter when confidence meets `SAARTHI_SIGNAL_DETECTION_MINIMUM_CONFIDENCE`, the response digest matches the submitted masked signal, the feature schema is supported, and the provider marks the evaluation `approved`. A detector failure returns orchestration HTTP 503 without consuming nudge budget; the same idempotency key can be retried.

## Fulfilment reconciliation

Every successful `/api/v1/actions/execute` transaction creates a `pending` reconciliation record atomically with the local `fulfilled` state. The worker queries the configured provider status API and records only a response digest plus operational metadata.

- `GET /api/v1/fulfillment/reconciliations` requires `ops` or `admin` and can filter by `pending`, `checking`, `matched`, `mismatch`, or `retry`.
- `POST /api/v1/fulfillment/reconciliations/{recommendation_id}/run` requires `ops` or `admin` and performs a concurrency-guarded provider check.
- `POST /api/v1/fulfillment/reconciliations/{recommendation_id}/acknowledge` requires `admin`. It records a pseudonymous operator reference and PII-masked note, but deliberately leaves the record in `mismatch` until a subsequent provider check matches.

`pending` and `processing` provider states become retryable. Provider outages release the claim with a bounded retry time. Completed responses match only when the provider reference equals the locally committed reference; reversals, failures, not-found responses, and reference differences remain discrepancies. See the [operations runbook](OPERATIONS_RUNBOOK.md).

## Operations cases

Operations cases are a governed handoff for reconciliation mismatches; they are not financial-action APIs.

- `POST /api/v1/operations/cases` requires `ops` or `admin`, an existing mismatch, and a short investigation summary. The summary is PII-masked and repeated requests for the same recommendation return the original case.
- `POST /api/v1/operations/cases/{case_id}/approve` requires `admin`. The approver must be a different authenticated principal from the requester.
- `POST /api/v1/operations/cases/{case_id}/submit` and `/sync` require `ops` or `admin`. The worker normally performs these actions automatically after approval.
- `GET /api/v1/operations/cases` requires `ops` or `admin` and supports status filtering.

Case responses omit requester and approver references. The SBI adapter sends no customer ID and uses the internal case ID as the downstream idempotency key. Only an allowlisted status envelope is persisted; arbitrary provider fields are discarded and the approved response is retained as a digest.

`/api/v1/policies` exposes approved policy metadata to `auditor`, `reviewer`, `ops`, or `admin`. `/api/v1/audit/integrity` verifies the retained pseudonymous hash chain. Review queue endpoints require `reviewer` or `admin`; customer identifiers are deliberately omitted from queue responses.
